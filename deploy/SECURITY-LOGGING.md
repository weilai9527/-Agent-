# 安全日志第一批变更

## 范围

- 两个 API 的 HTTP 请求生成服务端 `X-Request-ID`，调用方同名头不会覆盖它。
- `interview.operations` 向 stdout 输出 JSON 行，由现有 systemd/journald 收集。
- HTTP 请求记录 UTC 时间、服务、路由模板、认证后的操作者 ID、状态码、客户端 IP、响应完成情况和耗时。
- 记录学生登录、退出、首次改密、找回密码申请/验证/确认；记录 401/403/429、5xx、未完成响应及写操作失败。管理员既有审计操作同步进入新审计表，原表保留。
- 新增 `security_audit_events` 表和查询索引，不修改或删除历史表及记录，不自动清理新审计表。
- 新增仅超级管理员可见的“系统设置 → 安全审计”：服务端时间/事件/操作者/请求 ID 筛选，每页 50 条。接口 `/api/admin/security-logs` 最多每页 200 条。
- 意外异常在尚未发送响应头时返回通用 500，并返回请求 ID；部分发送的语音流保持异常语义，不伪造成功结束。

## 数据与可靠性

不采集请求/响应正文、Cookie、Authorization、查询参数、密码、重置 Token、完整简历、异常局部变量或包含实参的源码行。日志保留尝试登录的有效账号标识、认证后的账号 ID、IP 和业务对象 ID，仅用于受限审计。

未处理异常记录类型和调用位置，故意不直接保存可能包含密钥、SQL 值或个人信息的异常消息。第三方调用的既有 print/logger 输出尚未全部改造，不能将本次字段限制理解为整个旧日志系统已完成脱敏。

审计先输出结构化运行日志，再用独立连接写数据库，不提交/回滚业务事务。SQLite 锁等待 1 秒，MySQL 连接/读/写超时各 2 秒。写入失败记录 `security.audit_persist_failed`，包含同一 event_id/request_id，业务响应保持原语义。此机制提供失败证据，不保证数据库宕机期间的自动补写；补写队列属于下一阶段。

时间均为 UTC ISO 8601（毫秒）；页面按浏览器时区展示。查询需显式提供时区。分页固定查询截止时间以减少新增审计导致的翻页偏移。未知路由只记 `<unmatched>`；对象路径参数只采集名称以 `_id` 结尾且符合标识符规则的值。

## Nginx 配置

将 `deploy/nginx/security-logging.conf` 放入 http 上下文，例如 `/etc/nginx/conf.d/interview-security-logging.conf`。在本站 server 块启用：

```nginx
access_log /var/log/nginx/security-access.log interview_security;
```

格式包含 Nginx edge_request_id、上游响应中的 request_id、耗时、状态、来源和无查询参数的 URI。保留原日志文件作为历史证据，不截断或删除。新文件匹配现有 `/var/log/nginx/*.log` 轮转规则；本次不改变该规则的保留份数。

API 仍仅监听回环地址，由 Nginx 代理。客户端 IP 取 ASGI scope；部署时必须核对 Uvicorn 可信代理及 Nginx 转发头覆盖，不能把任意公网客户端提供的转发头当作身份依据。CORS 暴露 X-Request-ID，方便浏览器读取排错编号。

部署时两个 Uvicorn 服务追加 `--no-access-log`，由新的结构化访问日志替代默认访问行，避免默认访问行继续记录查询字符串。使用独立 systemd drop-in，回退时恢复原配置；不关闭应用错误日志或 systemd 日志。

## 发布与回退

1. 保留当前线上 Git 状态、待变更文件和 Nginx 配置备份。不得直接以本地整目录覆盖与本地不同的线上版本。
2. 用补丁预检确认只变更上述日志功能；在隔离数据库验证新表创建、审计写入及权限控制。检查管理端构建。
3. 确认无正在进行的实时会话，逐个更新并重启 API。首次启动仅新增表；不导入/覆盖业务数据。
4. Nginx 配置通过 `nginx -t` 后才 reload；更新管理端静态文件时保留旧资源以支持已打开的页面。
5. 用可区分的验收请求验证 X-Request-ID、结构化日志、新表记录、拒绝未授权查询，以及新 Nginx 行的关联编号。验收会自然产生审计记录。
6. 若验证失败，恢复本次备份的代码、前端入口和 Nginx 配置并恢复服务；保留新增审计表及已产生的日志，不以删表回退。
