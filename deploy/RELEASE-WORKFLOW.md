本机两套版本应分别理解：`main` 的已提交历史是旧版维护基线，`codex/refactor-microservices` 保存微服务开发成果。本分支 README 中的原生网关和独立服务说明描述的是重构代码，不代表线上已经采用该架构。远端默认分支继续为 `main`，普通克隆默认检出旧版；只有主动切换到重构分支才使用本开发快照。

## 2. 分支与发布版本的职责

| 分支或标记 | 用途 | 进入服务器的条件 |
| --- | --- | --- |
| `main` | 过渡阶段维护旧版；只合并已完成审核和验收的变更 | 从已验收提交建立发布标签后部署，不因分支名为 `main` 就视为可发布 |
| `fix/interview-f01-f08` | 完成旧版 F01～F08 和 RTC 修复，补齐本机发现的遗留场景 | PR 问题关闭并验收后合入 `main`，通过正式发布进入服务器 |
| `codex/refactor-microservices` | 保存和继续开发 Mac 上的微服务重构；接收必要的缺陷修复移植 | 完成微服务验收和数据迁移演练后，作为一次架构发布切换 |
| 发布标签，如 `vX.Y.Z` | 固定一次已验收的源码版本；标签对应完整提交 SHA | 部署记录同时保存标签、SHA 和实际构建产物标识；已发布标签不移动或覆盖 |

旧版日常发布顺序：**修复分支 → 审核与验收 → 合入 `main` → 标记发布版本 → 服务器部署该版本**。

微服务切换成功后，`main` 才转为微服务维护主线。若届时仍有学校使用旧版，应从最后一个旧版发布标签建立单独的旧版维护分支；按实际支持需要建立，不提前宣称两套架构已经合并。

## 3. 先保存本地重构，再处理旧版补丁

1. 记录桌面工作区当前分支、提交和改动清单，将现有重构保存在 `codex/refactor-microservices`。保留已有文件内容与改动归属，不用旧版文件覆盖重构。
2. 首次保存以完整保留可恢复的工作状态为目标，提交说明明确标注开发中、未完成上线验收。后续按服务或功能形成可审查的提交。
3. 提交源码、测试、依赖清单与锁文件、部署说明及 `.env.example`。真实 `.env`、密钥、数据库、日志、依赖目录、构建产物、`outputs/` 验收材料留在仓库外或现有忽略范围内。逐项检查新增文件，不强制加入被忽略的内容。
4. 旧版修复继续在独立且状态清楚的工作区处理。完成分支保存之前，不在桌面脏工作区直接执行拉取合并、切回旧版、硬重置或覆盖文件。
5. 分支建立、重构提交和推送完成后，更新本文的状态记录与对应 PR 链接。只有本地提交还不等于已有远端副本。

首次重构快照按上述规则保存在专属分支。后续是否同步远端，以 `git status --short --branch`、`git branch -vv` 和实际远端提交核对；本地提交不自动更新服务器。

## 4. 旧版补丁如何进入微服务

旧版修复与微服务改造涉及不同的入口和数据归属。先按缺陷场景移植行为与测试，再决定是否复用具体代码。

| 修复内容 | 微服务侧应核对的位置 |
| --- | --- |
| 服务端题目权威、回答绑定、提交去重与追问恢复 | `interview` 服务、网关契约及学生端提交逻辑 |
| 单题评分、报告版本、复核保护、迟到结果处理 | `assessment` 服务及管理端复核交互 |
| RTC 字幕去重、正式题目播报、换题与会话关闭 | `media`、`interview`、网关及学生端 RTC 代码 |
| 模型响应校验、备用供应商与用量 | 实际持有模型调用的服务及其与 `providers`、`usage` 的交互 |
| 导出转义、长输入处理 | 实际提供导出或解析的模块，以及对应回归测试 |

逐项记录“原缺陷 → 旧版修复提交 → 新服务实现 → 新架构复测结果”。前端虽然路径相同，也要核对接口、身份、轮次和报告字段；路径相同不保证可以直接复制或 cherry-pick。

重构分支可以按计划同步主线，但每次都要审查架构冲突，保留服务边界。禁止用旧 `backend/src/main.py` 或 `admin_backend/src/main.py` 整体替换新服务入口；也不能为消除冲突重新启用已经退出在线路径的旧后端。

## 5. 当前 PR 的发布阻断项

2026-11-05 对 `f6de2c4` 的本机独立测试确认：真实 Qwen 文字面试、评分、报告生成、管理端复核和下载能够运行；自动化累计 248 项及 4 个子用例通过，2 项 MySQL 专项因使用 SQLite 跳过。正常流程通过不代表下面两个边界已修复。

| 问题 | 本机复现 | 发布前要求 |
| --- | --- | --- |
| 历史已审核报告被重置 | 升级后的历史报告没有对应持久报告任务；再次请求结束面试后，审核状态从 `approved` 变为 `pending`，审核人和审核时间被清空 | 保留历史有效报告与审核信息；补充升级状态和重复结束的回归测试 |
| 追问失败后刷新卡住 | 任务失败后，页面刷新生成新的提交 ID；重交同一答案持续返回 409，仍停在原题 | 提供可恢复的提交身份或明确恢复流程；补充失败后刷新、重交和并发边界测试 |

两项都需要在新提交中修复，并用相同复现场景重新验收，再将该 PR 纳入发布候选。不能仅依据提交标题中的“修复”或已有测试总数认定问题关闭。

本次还观察到一次真实模型报告 JSON 解析失败，页面显示文字降级，重试后成功恢复。它是本次观测到的异常，尚未证明由该 PR 引入。真实 RTC 麦克风链路、生产 MySQL、长通话及评分质量的大样本校准未在本轮完成。

## 6. 服务器如何更新旧版

### 先确认服务器基线

在确认过的应用源码目录执行以下只读检查；如果服务器仅部署镜像或构建包，应从部署系统读取相同信息，不假定存在 Git 工作区。

```sh
git status --short --branch
git branch --show-current
git rev-parse HEAD
git describe --tags --exact-match HEAD
```

最后一条在没有精确标签时会报错，只表示当前提交未对应发布标签。部署标签时也可能处于 detached HEAD；此时以完整 SHA 和发布记录识别版本，不能仅凭没有分支名判断部署错误。

还需确认：当前应用目录或镜像、Python/Node 运行环境、进程管理方式与服务名、Nginx 路由、前端构建来源、配置注入位置、数据库版本与迁移情况。记录配置的来源和用途，不把密钥或密码抄入文档。

### 一次旧版发布的步骤

1. 在独立测试环境验收目标提交，包括登录、正常作答、失败重试、刷新恢复、真实评分、报告复核与下载。涉及数据库时，用对应数据库验证迁移兼容性。
2. 合并已验收的旧版修复，建立不可变的发布标签，记录完整 SHA、依赖版本、前端产物和部署配置版本。不要把本地未提交文件作为发布来源。
3. 备份现有业务数据，记录旧版本与迁移起点，保留上一版程序或镜像。确认迁移是否兼容旧程序以及是否需要停写。
4. 在新的发布目录、镜像或既有部署流水线中准备目标版本，复用受控配置；按服务器实际方式安装依赖、构建并检查启动。服务器上的临时改动先核实归属，不用强制覆盖代替确认。
5. 按既有发布方式切换程序和前端资源，重启对应进程并验证健康状态及实际业务请求。前端与 API 必须来自兼容版本。
6. 核对运行中的 SHA 或产物标识与目标一致；记录验收结果和异常，再结束本次发布。

| 已核实的部署方式 | 对应更新动作 |
| --- | --- |
| 源码目录 + 进程管理器 | 在独立发布目录准备指定标签，使用已确认的服务配置切换路径并重启；不在有业务数据或未提交改动的目录盲目拉取合并 |
| Docker 或其他镜像部署 | 从指定提交构建固定版本镜像，记录镜像摘要，按现有编排更新；数据卷与外部配置独立保留 |
| CI/CD | 由已确认的标签或发布入口触发构建部署，核对流水线使用的 SHA 和产物；开发分支提交不应直接触发生产切换 |

具体拉取、构建、重启及反向代理命令必须在确认服务器部署方式后补齐。本文不预设服务器使用 Docker、systemd、PM2 或某个目录，也不把一次 `git pull` 当作完整发布。

若现有流水线在 `main` 每次更新时自动部署，应先核实并调整发布触发条件，使发布版本可控，再将微服务合入主线。本文中的分支约定不会自动改变现有 CI/CD 配置。

## 7. 微服务完成后的架构切换

1. **准备独立环境。** 新服务使用独立端口、服务账户、配置和数据库，先以合成数据或校方脱敏副本验收；旧版生产流量继续使用原系统。
2. **完成业务与故障验收。** 验证校管、教师、学生的完整流程、租户隔离、服务端题目权威、任务去重恢复、评分与报告版本、复核、媒体会话及适用的证书流程。确认旧版必要补丁已移植。
3. **演练数据迁移。** 核对账号、组织、任课关系、答案、历史评分、报告审核及适用的证书/撤销记录，保留归属与数量校验。验证备份可恢复，明确迁移耗时和停写要求。
4. **固定发布版本。** 微服务变更通过审核后合入主线，建立架构发布标签；逐项记录服务启动顺序、数据库迁移、Worker、网关及 Nginx 切换方案。
5. **执行正式切换。** 在约定窗口停止旧系统写入并处理在途任务，以一致的备份点或已验证的增量水位完成迁移，再切换网关和前端。没有明确设计与验证时，不允许两套架构同时写同一批业务数据。
6. **上线复核。** 检查登录、存量记录、真实评分、报告复核、错误日志和任务积压，确认后再结束观察期。旧版本及迁移前备份按既定保留周期保存。

微服务具体运行、权限和数据要求见 [微服务运行边界](MICROSERVICES.md)、[分域 MySQL 部署](NATIVE-MYSQL.md)、[身份标识核验](MYSQL-IDENTIFIERS.md) 与 [恢复演练](RESTORE-DRILL.md)。

### 回退必须同时考虑程序与数据

在新版本尚未产生业务写入、且数据库仍兼容旧版时，可以按已验证方案切回上一版程序。若新版本已写入数据或执行不兼容迁移，不能只回退 Git 提交或切回 Nginx：应先停写并保全新增记录，按演练过的数据转换或恢复方案处理，再决定恢复哪个版本。直接恢复旧备份会丢失备份之后的数据，必须先核对这部分数据的保留方式。

## 8. 每次发布保留的记录

将以下字段随发布记录保存，测试结论必须指向同一个提交或产物：

| 字段 | 内容 |
| --- | --- |
| 环境与时间 | 测试/生产、服务器标识、北京时间 |
| 发布版本 | 标签、完整提交 SHA、镜像摘要或构建产物标识 |
| 架构 | 旧版或微服务版，以及本次更新的服务范围 |
| 来源 | 对应 PR、缺陷编号、修复及移植记录 |
| 验收 | 实际通过、失败、跳过和未验证项；区分真实供应商调用与测试替身 |
| 数据 | 迁移版本、一致备份点、恢复验证结果 |
| 配置 | 配置版本与保管位置，不记录密钥内容 |
| 回退 | 前一版本、回退条件、新写入数据处理步骤 |
| 执行结果 | 执行人、运行版本核对结果、上线业务检查及异常处理 |

完成本次开发快照保存后，待办按顺序为：修复旧版 PR 的两个遗留问题 → 验收并发布旧版补丁 → 在微服务中逐项移植与复验 → 完成迁移演练后切换架构。服务器基线核实可以与开发并行进行。
