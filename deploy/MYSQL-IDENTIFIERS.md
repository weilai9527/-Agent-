# MySQL 服务身份标识的排序规则

租户、职员、学生和对象标识按签名的原始值比较。MySQL 8 的服务表使用 `utf8mb4_bin` 或 `utf8mb4_0900_bin` 保存这些键，服务标识不接受空白。新建专有数据库时可指定 `CHARACTER SET utf8mb4 COLLATE utf8mb4_bin`。已有库的默认排序规则即使是 binary，也不能证明列本身安全。启动检查查询 `INFORMATION_SCHEMA.COLUMNS`，逐列验证允许的排序规则，缺列或不匹配时拒绝启动。普通检索文本、职位描述、展示姓名的排序无需更改。

使用只读账号与对应的 `<服务名>_DB_ENGINE=mysql`、`<服务名>_MYSQL_*` 配置运行下列命令。检查不会执行 DDL 或读取学生资料。career 使用现有学校与数据库的映射。assessment 仅对独立评估库执行。共享的旧面试兼容库和它的外键不使用这条独立评估库契约。

```sh
python scripts/check_mysql_identifiers.py identity
python scripts/check_mysql_identifiers.py career
python scripts/check_mysql_identifiers.py assessment
```

## 已有实例

1. 先在只读快照上执行检查，记录返回的不安全表、列。停止旧写入、worker 和验真流量后保存一致性备份。在新的专有数据库按本版服务 DDL 初始化空表。复制表内容时保留数据原值，避免将旧表定义覆盖到新库。
2. 从受信的学校名单、原签发者、审计记录核实每条归属和关联键。旧库曾用大小写/重音不敏感比较时，不同主体可能命中了同一行或一个外键；更改排序规则不能恢复已经混同或覆盖的记录。对无法确定归属的记录隔离处理。
3. 按外键依赖顺序导入数据，保持外键校验启用。使用 binary 按学校及主体分组核对行数、唯一键、父子关系、授权与证书。重新运行该服务检查，验证相似名称的账号彼此不可查询或写入，再切换该域 API 和 worker。业务域的独立迁移规则仍然适用，备份和旧库保留供回退与核对。
4. 历史面试库仍按单学校实例绑定；原生账号映射会核验数据库中实际返回的用户 ID，旧主键发生等价冲突时拒绝绑定。career 按学校使用独立数据库，保留既有目录表的历史排序，验证学校标记和两张按学生过滤的表的实际用户标识列。profile 只要求自身明确声明的学校与主体列。
